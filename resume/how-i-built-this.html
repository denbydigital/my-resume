How I built this

A live demo of AI-assisted delivery — this site itself.

Every page on this site was built through conversation with Claude. Here's the step-by-step of how I did it, because the process is as much part of my practice as the output.

I'm an IT Business Analyst. I don't write production code for a living — I analyse, translate and facilitate. What I do know how to do is describe a problem precisely, iterate quickly on feedback, and spot when something isn't right. It turns out those are exactly the skills you need to build with AI.

The build

Step by step, start to finish.

Step 1  ·  Brand & direction

Starting with a brief, not a blank canvas

I didn't hand Claude a brief and say "make me a website." I described what I didn't want — contractor-dark, blue, boring tech-resume energy — and what I did: something that looked more like a design portfolio, reflected the work I actually do, and felt like me.

We landed on the Ink & Leaf direction: deep forest green primary, warm amber gold accent. I approved the palette, the font pairing (Newsreader serif + Hanken Grotesk sans), and the overall mood before a single page existed.

Step 2  ·  Design system

Building a token-based design system from scratch

Claude generated a complete CSS custom-property token system — colours, spacing, typography, radii, shadows — all in OKLCH colour space for perceptual consistency. The rule was: no hardcoded hex or rgb values anywhere in the site. If it's a colour, it comes from a token.

That discipline meant that when I changed my mind about a tint, it updated everywhere. As a BA I spend a lot of time building traceability. This was the same idea, applied to a design system.

Step 3  ·  Page architecture

Six inner pages and a landing — structured like a product

I scoped the site the same way I'd scope a product: define the pages, the purpose of each, and what a visitor should take away. About, Experience, AI Practice, Portfolio, Credentials, Contact — each with a clear job to do.

Claude built shared layout infrastructure (site.js injects the header, footer and mobile nav into every page via a single JS file) so the structure is maintained in one place. Exactly the kind of single-source-of-truth I'd argue for in any delivery.

Step 4  ·  Portfolio data

13 projects, structured as data, not markup

Rather than hardcoding each portfolio entry into HTML, Claude architected a portfolio-data.js data file. Every project — title, blurb, tags, detail bullets, features, logo — lives in one structured array. The portfolio page renders them dynamically, including a slide-up modal for detail.

When I wanted to rename projects, reorder them, or add two new entries (Queensland Law Society and Lite 'N Easy), it was a data change, not a markup surgery. That's the kind of separation-of-concerns I'd advocate for in any system design.

Prompt I used "DoctorChat can be renamed to DrTalk, ThinkClear can be renamed to Clear Horizon, Recruitment AI Automation can be renamed to SHK AI, Customer Portal can be renamed to Queensland Law Society, Website UI Uplift can be renamed to Lite 'N Easy. You can remove the dates from everything and the company against them."
Step 5  ·  Iteration

Shipping fast, then improving in conversation

The landing page originally had a large decorative "L" watermark I didn't like. I pointed at a screenshot and said exactly that. Claude removed it and suggested replacing it with a circular headshot. I said yes. That interaction took about 60 seconds.

This is the part most people miss when they talk about AI — it's not about generating a thing once. It's about being able to describe what's wrong and iterate in real time, the same way you'd work with a developer in a sprint review.

Step 6  ·  Assets

Logos, photography and visual polish

I sourced and added 12 company logos to the assets folder, then asked Claude to wire them into the portfolio cards and modals. That meant updating the data schema, the card render template, the modal open function and the CSS — all consistent, all working, in one pass.

When logos didn't appear on the live site, we debugged it together: they'd been created locally but never committed to git. Identified, explained, fixed.

Step 7  ·  Deployment

GitHub and GitHub Pages, managed through conversation

The whole project is version-controlled in Git and deployed to GitHub Pages. I created the repo and set up Pages myself; everything after that — branching, committing, raising PRs, merging — was done through Claude in the terminal.

When I wanted a change live, I'd say "PR please." When I wanted to merge it, I'd say "merge." I didn't write a single git command manually.

Step 8  ·  Beyond the site

A cover letter, written and formatted as a PDF

Once the site was up, I used the same session to draft a cover letter for a role I was excited about. I described the company, shared what I genuinely love about their brand, mentioned I live locally, and asked for a PDF with my headshot. Claude wrote it, generated the PDF with pdfkit, and iterated on tone, formatting and length until it fit on one page.

That's the broader point: the same AI-assisted workflow that built this site is the one I bring to delivery work every day.

The tools

What I actually used

  • Claude Code — desktop app, agentic mode
  • HTML, CSS, vanilla JS — no framework, no build step
  • Git + GitHub Pages — version control and hosting
  • pdfkit (Node.js) — PDF generation for the cover letter
The practice

What made it work

  • Describing outcomes, not solutions
  • Reviewing output critically before approving
  • Iterating fast on feedback instead of re-specifying
  • Keeping a single source of truth for data and tokens
